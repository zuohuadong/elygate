This is the recommended deployment profile for small and medium-sized teams. It runs one Elygate process and one PostgreSQL instance on a single server. Kubernetes, Redis, an external queue, and object storage are not required.

## Architecture

```text
reverse proxy (optional)
        |
        v
Elygate :8080
        |
        v
PostgreSQL 16+
```

PostgreSQL stores configuration, governance data, logs, usage ledger records, audit events, and durable background jobs. Elygate uses database transactions and advisory locks for coordination. Redis is only an optional vector-store backend; use pgvector when semantic caching is required without another service.

## Files

The repository includes a runnable template in `examples/single-node-postgres`:

```text
examples/single-node-postgres/
  .env.example
  config.json
  docker-compose.yml
```

Create the local environment file and replace every placeholder before starting:

```bash
cd examples/single-node-postgres || exit
test -e .env || cp .env.example .env
chmod 600 .env
mkdir -p -m 700 backups
bash ../../scripts/production/single-node-preflight.sh . && docker compose up -d
```

Do not commit `.env`. Keep `ENCRYPTION_KEY` stable across restarts, upgrades, backups, and restores.

Replace the placeholders before running the preflight. It checks private file permissions,
immutable image references, storage settings, enabled command health checks, restart
policies, and the gateway's dependency on PostgreSQL health. The local PostgreSQL service
must not publish host ports or use host networking. This static check does not start
containers, verify the health probe's behavior, create a backup, or establish recovery readiness.
If a private `backups` directory already exists, retain it rather than replacing it.

## Verify

```bash
curl --fail --show-error http://127.0.0.1:8080/health
docker compose ps
docker compose logs --tail=100 elygate
```

After the initial administrator setup, create a Project and Application, bind a Virtual Key, send one non-streaming request and one streaming request, then confirm the request appears in Usage Ledger and Audit.

## Backup

Back up PostgreSQL before every upgrade. Stop Elygate and exclude all other writers for a consistent backup window. Confirm a normal gateway shutdown before taking the backup; do not continue after a failed command.

The default template uses the same `POSTGRES_DB` for configuration and logs, so one dump covers both stores. If you configured separate databases, dump and restore both while all writers remain stopped. A database dump alone does not preserve local uploads, Skills files, or external encryption/signing material.

Stop the gateway yourself, exclude every other database writer, and verify a normal
exit before invoking the repository backup entry point. It never stops, starts, drops,
or overwrites a service or database:

```bash
(
set -eu
docker compose stop --timeout 60 elygate
test "$(docker inspect --format '{{.State.ExitCode}}' "$(docker compose ps -aq elygate)")" = 0
BACKUP_ROOT="$PWD/backups" \
  bash ../../scripts/production/single-node-backup.sh . --confirm-no-writers
docker compose start elygate
)
```

The command requires the explicit `--confirm-no-writers` acknowledgement, checks the
default single-database PostgreSQL topology, normally stopped gateway, healthy database
and actual container image/environment/mounts against Compose. The running image must
use the repository's standard entrypoint and command, with exactly one actual
`APP_DIR=/app/data`; stale overrides from an older container are rejected. It writes a custom
`pg_dump` archive, lists it with `pg_restore --list`, streams `/app/data` into
`runtime.tar` without extracting it on the host, and records both container image
references/IDs and SHA-256 checksums. The tar retains runtime ownership and permissions.
It rejects deployment-file changes and container restarts during capture.
No `.env` or raw rendered Compose/inspect output is archived. Runtime files and dumps
remain sensitive. An incomplete run is removed; only a complete capture is published,
with `recovery_verified: false` in its manifest. A failure leaves the gateway stopped
for operator investigation instead of automatically restarting it.

`pg_dump` expands credentials inside the selected PostgreSQL container and connects to
its loopback port, rather than trusting `PGHOST` or host-shell variables. It does not
require sourcing `.env`. Do not print rendered Compose configuration or use shell
tracing when credentials are present. Set `ENV_FILE` or `BACKUP_ROOT` for alternate
private paths; the backup root must already exist with mode `0700`. Custom dual-database
or external PostgreSQL profiles require separate reviewed backup procedures and are
rejected by this entry point.

Retain the exact Elygate image digest and configuration with the backup. Keep `.env`, `ENCRYPTION_KEY`, and any separately configured audit-signing or storage credentials through your secret-management process, with access restricted to recovery operators. Do not commit backup files, put `.env` in the dump archive, or publish backup contents. Keep the entire backup directory private; runtime files and database dumps can contain sensitive data.

Listing the dump only checks that its archive can be read. Restore and reconcile it on an isolated target before treating it as a verified backup.

## Restore

Restore only on a separate test server or explicitly isolated deployment with new
PostgreSQL and runtime volumes. Keep the original databases, files and image intact.
Use a different Compose project name and different `container_name` values for both
services. Change the gateway's published port to an unused loopback-only port.
Use fresh, distinct local volumes without driver options; never point an external
volume declaration at an existing source volume. Exclude every other client and
writer from the recovery database for the entire operation.

Copy the backup's `config.json` into the isolated deployment unchanged, and restore
the original `.env` values, including database credentials and stable encryption/signing
material, through secret management. A different project and new volumes provide the
isolation; the database name inside the isolated PostgreSQL instance stays unchanged.
Use the exact backed-up image references and image IDs for both services. Do not
print secrets or rendered Compose/inspect output.

The repository restore entry point requires Docker Compose, `jq` and Python 3.
Only use backups from a trusted source: SHA-256 checksums detect corruption, not
authenticity, and PostgreSQL dumps can execute database code. Existing backups
without source project/container/volume identity in `manifest.json` are rejected;
there is no legacy restore fallback.

From the prepared isolated Compose directory, start only PostgreSQL and create,
but do not start, the gateway. These commands assume `ENV_FILE` is unset or points
to this target's private `.env`, and that all names, volumes and ports were already
changed as described above:

```bash
(
set -eu
backup_dir="/private/path/to/elygate-backup"
target_dir="$PWD"
bash /path/to/elygate/scripts/production/single-node-preflight.sh "$target_dir"
docker compose up -d --wait --wait-timeout 120 postgres
docker compose create --no-deps elygate
bash /path/to/elygate/scripts/production/single-node-restore.sh \
  "$backup_dir" "$target_dir" --confirm-isolated-no-writers
)
```

The entry point checks the complete private artifact set and checksums, archive paths
and links, source/target identity, actual container images/environment/mounts, an
empty runtime volume, and a database with no user objects or other connected clients.
Absolute paths, parent-relative link targets, duplicate entries, entries below links,
special files and setuid/setgid permissions in `runtime.tar` are rejected. Internal
symbolic links and hard links to archived regular files are allowed.

It imports SQL transactionally with `--exit-on-error`, then imports runtime files
into the new volume using a stopped temporary container and `docker cp -a`, preserving
ownership and permissions without extracting onto the host. It does not overwrite
the separately mounted `config.json`, start the gateway, drop/clean a database or
modify source services. Failure can leave a partially restored target: retain that
target isolated for investigation. Do not retry against its now nonempty volumes,
delete production data or treat a successful import as verified recovery.

Only after all stores, files and secrets are restored, start the isolated gateway. Verify database-backed `/health`, administrator login, Application Key bindings, Usage Ledger, audit history, local files and encrypted credentials. Exercise a new authorized write, verify the original source has not changed, and record cleanup of the test target.

A backup that has never been restored is not recovery evidence. This guide and a readable dump alone do not prove full recovery, crash safety, version upgrades or production acceptance.

## Upgrade and rollback

1. Record the current image tag or digest.
2. Create and verify a PostgreSQL backup.
3. Pull or build the new fixed image version.
4. Run `docker compose up -d --no-deps --force-recreate elygate`.
5. Verify `/health`, administrator login, one inference request, Usage Ledger, and Audit.
6. If verification fails, restore the previous image. Restore the database backup only when the failed version ran an incompatible migration or changed persistent data.

Avoid production `latest` tags. Use an immutable version or image digest so rollback selects the exact previous build.

## Operational boundaries

- This profile intentionally runs one Elygate process. There is no automatic gateway failover.
- PostgreSQL may run on the same server or an external managed server.
- TLS should terminate at a reverse proxy when the service is exposed outside a trusted network.
- Set log retention according to disk capacity. PostgreSQL logs and audit tables grow independently of container filesystem usage.
- External KMS, WORM storage, SBOM verification, and Kubernetes are optional customer-specific extensions, not prerequisites for this profile.
