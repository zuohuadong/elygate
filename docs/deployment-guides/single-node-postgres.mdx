This is the recommended deployment profile for small and medium-sized teams. It runs one Elygate process and one PostgreSQL instance on a single server. Kubernetes, Redis, an external queue, and object storage are not required.

## Architecture

```text
reverse proxy (optional)
        |
        v
Elygate :8080
        |
        v
PostgreSQL 16+
```

PostgreSQL stores configuration, governance data, logs, usage ledger records, audit events, and durable background jobs. Elygate uses database transactions and advisory locks for coordination. Redis is only an optional vector-store backend; use pgvector when semantic caching is required without another service.

## Files

The repository includes a runnable template in `examples/single-node-postgres`:

```text
examples/single-node-postgres/
  .env.example
  config.json
  docker-compose.yml
```

Create the local environment file and replace every placeholder before starting:

```bash
cd examples/single-node-postgres || exit
test -e .env || cp .env.example .env
chmod 600 .env
mkdir -p -m 700 backups
bash ../../scripts/production/single-node-preflight.sh . && docker compose up -d
```

Do not commit `.env`. Keep `ENCRYPTION_KEY` stable across restarts, upgrades, backups, and restores.

Replace the placeholders before running the preflight. It checks private file permissions,
immutable image references, storage settings, enabled command health checks, restart
policies, and the gateway's dependency on PostgreSQL health. The local PostgreSQL service
must not publish host ports or use host networking. This static check does not start
containers, verify the health probe's behavior, create a backup, or establish recovery readiness.
If a private `backups` directory already exists, retain it rather than replacing it.

## Verify

```bash
curl --fail --show-error http://127.0.0.1:8080/health
docker compose ps
docker compose logs --tail=100 elygate
```

After the initial administrator setup, create a Project and Application, bind a Virtual Key, send one non-streaming request and one streaming request, then confirm the request appears in Usage Ledger and Audit.

## Backup

Back up PostgreSQL before every upgrade. Stop Elygate and exclude all other writers for a consistent backup window. Confirm a normal gateway shutdown before taking the backup; do not continue after a failed command.

The default template uses the same `POSTGRES_DB` for configuration and logs, so one dump covers both stores. If you configured separate databases, dump and restore both while all writers remain stopped. A database dump alone does not preserve local uploads, Skills files, or external encryption/signing material.

```bash
(
set -eu
umask 077
backup_dir="elygate-backup-$(date +%Y%m%d-%H%M%S)"
mkdir -m 700 "$backup_dir"
docker compose stop --timeout 60 elygate
test "$(docker inspect --format '{{.State.ExitCode}}' "$(docker compose ps -aq elygate)")" = 0
docker compose exec -T postgres \
  sh -ec 'exec pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' \
  > "$backup_dir/database.dump"
docker compose exec -T postgres pg_restore --list \
  < "$backup_dir/database.dump" > "$backup_dir/database.list"
mkdir -m 700 "$backup_dir/runtime"
docker compose cp elygate:/app/data/. "$backup_dir/runtime/"
cp config.json docker-compose.yml "$backup_dir/"
docker compose start elygate
)
```

The quoted `sh -ec` command expands credentials inside PostgreSQL's container, where Compose has injected them. It does not require sourcing `.env` in the host shell. Do not print rendered Compose configuration or use shell tracing when credentials are present.

Retain the exact Elygate image digest and configuration with the backup. Keep `.env`, `ENCRYPTION_KEY`, and any separately configured audit-signing or storage credentials through your secret-management process, with access restricted to recovery operators. Do not commit backup files, put `.env` in the dump archive, or publish backup contents. Keep the entire backup directory private; runtime files and database dumps can contain sensitive data.

Listing the dump only checks that its archive can be read. Restore and reconcile it on an isolated target before treating it as a verified backup.

## Restore

Restore only on a separate test server or explicitly isolated deployment with new PostgreSQL and runtime volumes. Keep the original databases, files and image intact. Configure that target's `.env` and `config.json` with a new database name and the original stable encryption/signing material. Use the exact Elygate image version that produced the backup for the first recovery boot.

The following is the database-import step, not a complete environment restore. In the isolated deployment, Compose creates `POSTGRES_DB` only when PostgreSQL's data volume is empty. Confirm the target is empty before importing. The command below waits for its configured health check; never point these commands at the only production copy.

```bash
(
set -eu
backup_dir="/private/path/to/elygate-backup"
docker compose up -d --wait --wait-timeout 120 postgres
docker compose ps postgres
docker compose exec -T postgres \
  sh -ec 'exec pg_restore --exit-on-error --single-transaction --no-owner --no-acl \
    -U "$POSTGRES_USER" -d "$POSTGRES_DB"' \
  < "$backup_dir/database.dump"
)
```

Do not drop or clean the original database to make a restore succeed. An import conflict or error must abort recovery; inspect the isolated target rather than deleting production state.

Before starting Elygate, also restore the backed-up local runtime files into the new runtime volume, preserve their required ownership and permissions for the chosen image, and restore `config.json` through its separate read-only mount. Restore the stable encryption/signing material through the target's secret-management process. Do not assume importing SQL restores uploaded files or makes encrypted values readable.

Only after all stores, files and secrets are restored, start the isolated gateway. Verify database-backed `/health`, administrator login, Application Key bindings, Usage Ledger, audit history, local files and encrypted credentials. Exercise a new authorized write, verify the original source has not changed, and record cleanup of the test target.

A backup that has never been restored is not recovery evidence. This guide and a readable dump alone do not prove full recovery, crash safety, version upgrades or production acceptance.

## Upgrade and rollback

1. Record the current image tag or digest.
2. Create and verify a PostgreSQL backup.
3. Pull or build the new fixed image version.
4. Run `docker compose up -d --no-deps --force-recreate elygate`.
5. Verify `/health`, administrator login, one inference request, Usage Ledger, and Audit.
6. If verification fails, restore the previous image. Restore the database backup only when the failed version ran an incompatible migration or changed persistent data.

Avoid production `latest` tags. Use an immutable version or image digest so rollback selects the exact previous build.

## Operational boundaries

- This profile intentionally runs one Elygate process. There is no automatic gateway failover.
- PostgreSQL may run on the same server or an external managed server.
- TLS should terminate at a reverse proxy when the service is exposed outside a trusted network.
- Set log retention according to disk capacity. PostgreSQL logs and audit tables grow independently of container filesystem usage.
- External KMS, WORM storage, SBOM verification, and Kubernetes are optional customer-specific extensions, not prerequisites for this profile.
